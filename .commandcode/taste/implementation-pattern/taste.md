# implementation-pattern
- When extending a small zero-dependency tool/script (e.g., a Node server with no packages), preserve its zero-dependency character — implement new features (log rotation, retention caps) with the language's built-ins rather than adding libraries, and follow the existing code's style: tunable constants read from env vars with sane defaults and a documented `0`/disable sentinel, never hardcoded thresholds. The same rule applies to Python scripts — e.g., a Telegram bridge posts HTTP events with stdlib `urllib.request` rather than adding `requests`/`httpx`. Confidence: 0.8
- For decoupled orchestration between separate long-running processes (e.g., a Node monitor server and a Python bridge), use a durable file-based outbox (append-only JSONL the consumer polls on an interval) instead of HTTP calls or shared in-memory state — it adds no dependencies, survives restarts, and matches an existing JSONL event-log pattern. Pair each request's lifecycle (queued → running → done) by a stable id written into both the outbox line and the emitted events, and serialize concurrent executions with a single shared lock across all producers. Confidence: 0.7
- Optional/observability integrations (e.g., a Telegram bridge posting activity events to a monitoring dashboard) must be best-effort: wrapped in try/except with a short timeout, never blocking or breaking the primary flow when the downstream service is down or slow. Confidence: 0.78
- When the user selects named sections from a categorized plan (e.g., "Modern checkout UX" and "Trust signals"), implement ALL items within those sections in one cross-layer pass (frontend + backend) — do not ask for further step-by-step approval on individual sub-items within a named section the user already endorsed. Confidence: 0.85
- When adding a new field to a backend DTO/record that is displayed in frontend UI, propagate it through ALL layers in the same coordinated pass: backend DTO definition → frontend TypeScript type → frontend response parser/extractor → UI component display → adjust CSS layout (grid columns, spacing, width) to accommodate the new element. Do not land a backend change and leave the frontend parsing it as an opaque blob or breaking layout. Confidence: 0.80
- When implementing checkout/payment flow UI improvements, apply both layers in parallel: backend changes (security, API, DTOs) and frontend changes (components, actions, pages) in the same pass — the user expects a coordinated ship, not separate frontend/backend phases. Confidence: 0.80
- When a brainstorm plan identifies "quick wins" (low-effort, high-impact items), implement them immediately alongside the primary feature work, not deferred to a separate follow-up task. Quick wins include: passing callback URLs to providers, adding idempotency keys, origin validation, stricter rate limiting, trust indicators, countdown timers, replacing insecure storage (sessionStorage), progress indicators, success animations, skeleton loading, and security headers middleware. Confidence: 0.80
- Business validation limits and thresholds (e.g., import weight tolerance, max file size, max rows) should be configuration-driven via an options class bound with `IOptions` + `ValidateOnStart`, never hardcoded in code. Reaffirmed when pagination page settings became a `PaginationOptions` class (registered in Program.cs with `ValidateOnStart`) following the same pattern. Confidence: 0.8
- When a default value becomes configuration-driven (e.g., pagination page/pageSize), use a `0 = "use the configured default"` sentinel: controllers default the query params to 0, and the single resolution point (the repository) substitutes the configured default and clamps to the configured max. Do not reintroduce literal defaults in controllers or re-clamp in the service layer — the service echoes `Math.Max(1, value)` only, since the repo already resolved and clamped. This keeps the config the single source of truth. Confidence: 0.7
- For simple file formats (CSV), prefer a hand-rolled deterministic parser with no new dependency; add a small MIT library (ClosedXML) only for genuinely complex formats (.xlsx). This was reaffirmed when building a second CSV feature (delivery-requests) that copied the existing hand-rolled `splitCsvLine` parser instead of adding a library. Confidence: 0.7
- For app auth in this stack (ASP.NET Core API + Next.js frontend), use JWT bearer auth on the backend (BCrypt-hashed passwords, `[Authorize]` on data controllers, signing key overridable via env) with the JWT stored in an httpOnly cookie on the Next side and route protection in the proxy file. Keep the MVP auth surface minimal per user preference: login-only with DB-seeded accounts (no registration flow) and gate-only access (require auth but defer per-user data scoping). The user confirmed all three of these decisions (login-only, gate-only, new dashboard page) before implementation. Confidence: 0.85
- For bulk/batch operations (e.g., multi-model file imports), use per-item partial-success semantics: persist the valid items, skip the invalid ones with item-level errors, and return per-item results — one bad item must not block the rest. Confirm the atomicity scope (per-item vs all-or-nothing) with the user upfront. Confidence: 0.7
- Import/reconciliation flows should auto-provision missing reference data (e.g., securities with ticker/SEDOL/ISIN from the file) rather than rejecting unknown identifiers or requiring manual entry — persist the reference row and link records via FK, backfilling identifiers when the file supplies them. Confidence: 0.6
- Prefer native platform primitives over adding a third-party dependency for UI interactions — e.g., native HTML5 drag-and-drop instead of a drag-and-drop library, with an explicit "no new dependency — keeps the bundle lean and matches MVP scope" justification. Confidence: 0.6
- When adding a complementary/symmetric operation to an existing one (e.g. activate↔deactivate, enable↔disable, archive↔unarchive), mirror the existing sibling method exactly across all layers: identical async signature + return type, the same user-scoping/auth guard (e.g. `UserId` equality check), the same null-return-on-failure semantics, and the same logging conventions. Add matching unit tests following the sibling's Arrange/Act/Assert shape — and keep the new method placed adjacent to its sibling so the symmetry is self-documenting. Confidence: 0.9
- A symmetric backend operation must be matched by a symmetric frontend mirror: the server action should reuse the sibling action's response-shape (`{ data?, error? }`), the same `authFetch` + PascalCase→camelCase raw-type mapper, and the same optimistic update + revert-on-error UX that the sibling action established. Never ship one direction without the other. Confidence: 0.88
- HTTP helpers (authFetch/apiFetch wrappers) must treat 204/205 responses — or any empty-body response (`content-length: 0`) — as success and return without parsing JSON. Calling `res.json()` on a 204 throws "Unexpected end of JSON input", which turns a successful DELETE into an error and makes optimistic UIs revert the change (this surfaced twice as "unmap/remove mapped model not working" while the backend 204 + DB row removal were correct all along). Check status/content-length before reading the body. Confidence: 0.85
- Reuse existing shared server actions (and their response mapping) as the single source of truth for a resource's fetch logic across pages, rather than re-implementing fetch + PascalCase→camelCase mapping per page — keep one data module per domain (e.g., import/actions) and import it from sibling pages so all consumers stay consistent. Deduplicate duplicate wrapper actions (e.g., three near-identical `searchModels` wrappers) into the canonical module and repoint all importers in the same pass. Confidence: 0.75
- Build JSON payloads (e.g., notification event payloads stored as strings) with `JsonSerializer.Serialize` over anonymous objects instead of hand-interpolated JSON strings (`$"{{\"runId\": {id}}}"`) — embedded free text such as error messages containing quotes silently breaks string-built JSON. Confidence: 0.65
- When spawning child processes in Node on Windows, never resolve the shell via bare PATH names like `"cmd.exe"` — use `process.env.ComSpec` (the absolute cmd.exe path Windows always sets) with `"cmd.exe"` only as fallback, since a broken/stripped PATH makes the spawn throw ENOENT. Confidence: 0.85
- Attach an `error` listener to EVERY spawned child process (all platforms), not just in a try/catch — an unhandled `'error'` event on a child (e.g., spawn ENOENT emitted asynchronously) is fatal and crashes the entire Node server, not just the request. Spawn failures must be logged as best-effort, never thrown. Confidence: 0.9

# csv-validation
- CSV row-level validation errors are numbered by 1-based data-row index (the first row after the header is row 1; the header and blank lines are not counted) — this is the established convention across services (ImportService and DeliveryRequestService). The frontend file-preview ROW column and the error→row map MUST use the same numbering as the backend, or errors silently land on the wrong displayed row. When a bug is reported as "errors don't map to the right row", check the frontend offset assumption (e.g., `i + 2` for header) against the backend's `index + 1` first. Confidence: 0.7

# delivery-workflow
- Prefer a two-phase delivery flow over immediate one-click generation: actions queue requests to a tracker as PENDING (e.g., a sponsor page's "Add to tracker" queues the sponsor's active pairings instead of "Run delivery now" executing them), and a separate "Initiate delivery" step on the tracker creates and runs the batch. Queue operations should be idempotent — skip pairings that already have a PENDING request and report how many were newly queued. Confidence: 0.65

# charting
- When a page needs a chart, use recharts (the explicitly approved choice) rather than hand-rolling SVG — a chart library is a justified dependency for visualization even though native primitives are preferred for ordinary UI interactions. Expect a recharts v3 Tooltip formatter typing adjustment (value type is broader than `number | string | undefined`). Confidence: 0.55

# list-filtering
- Inclusive date-range filters on list endpoints follow a standard convention: `from` is start-of-day inclusive (`CreatedAt >= from`), and `to` is end-of-day inclusive implemented as an exclusive upper bound (`CreatedAt < to.Date.AddDays(1)`). Both are optional `DateTime?` params defaulting to null, threaded through repository → service → controller, and applied in the repository's LINQ `Where` before `CountAsync`/`Skip`/`Take` so filtering stays server-side. When the date-range query runs against a growing table, document a composite index (e.g., `DeliveryRuns (UserId, CreatedAt)`) as a candidate in the API notes. Confidence: 0.6
- When a Python long-running service runs a background worker thread alongside a library that creates its own event loop in the main thread (e.g., python-telegram-bot's `app.run_polling()`), never call `asyncio.set_event_loop()` in the main thread — it binds a loop that the library then sees as "This event loop is already running" and crashes on startup. Create the loop, bind it, and create the task ONLY inside the worker thread (thread target does `asyncio.set_event_loop(loop)` + `loop.run_forever()`), leaving the main thread's loop untouched for the library to own. Confidence: 0.85
- When adding special commands to an AI-agent bridge (e.g., Telegram → command-code), the user prefers explicit command handlers in the bridge (parse arguments, dedicated flow, e.g., a `/plan` CommandHandler) over letting the agent interpret all raw `/commands` — unknown commands stay filtered/ignored, and the special command is registered before the generic message handler so it is captured first. Confidence: 0.6
- Configurable path/env defaults must resolve to a real, derived location (e.g., WORKDIR defaults to the repo root relative to the script's own path), never a placeholder like `C:\path\to\your\project` — a placeholder default silently breaks the first run in any terminal without the env var. Validate such config at startup (fail fast with a clear message) instead of crashing mid-operation on first use. Confidence: 0.65
- For commands that create artifacts/files through an agent (e.g., `/plan` via Telegram), the user prefers a draft-then-confirm flow: the agent produces the draft in chat first, and the file is only written after the user explicitly replies confirm (with cancel to discard) — never write files on the first command. Keep pending drafts in a per-chat map between messages. Confidence: 0.65
- For agent-bridge conversation continuity, track sessions per chat/thread and persist the mapping across restarts (e.g., a small JSON file), so each conversation resumes its own session via `--resume <sessionId>` rather than one global "resume most recent" thread. Confidence: 0.6
- For agent-bridge session resumption, the failure path matters as much as the happy path: when `--resume <id>` fails because the stored session no longer exists ("No session ... found to resume"), the bridge must detect it, retry fresh without the resume flag, record the new session, and clear the stale per-chat mapping in EVERY caller that holds it (main message path and outbox path alike) — otherwise the dead session is retried on every message. A stale-session error should never surface to the user; it must degrade into a working fresh-session reply. Confidence: 0.7
- CLI-wrapper fallback detection (e.g., deciding when to retry an external CLI without its resume/continue flags) must scan ALL channels an error can arrive through — the wrapper's parsed error field as well as stdout/stderr — because a check that only inspects stdout/stderr silently misses failures whose message flows through the parsed error channel (this was caught by a mock test that placed the error in `error_text`). Confidence: 0.7
- For agent-bridge (Telegram) interactions, the user prefers tappable inline keyboard buttons over typing replies: plan drafts get Save/Cancel buttons and every agent reply gets a quick-action row (Continue, Open terminal, New plan, Status), with the typed fallbacks (confirm/cancel) still working. Buttons are chat-allowlisted and callback queries are answered immediately so the button doesn't stay spinning. Confidence: 0.65
- When computing live "running/active" counts from paired start/end events in an event log, treat started-but-never-ended items as stale once their start is older than a configurable threshold (default = operation timeout + margin, `0` disables) — runs abandoned by a crashed/restarted daemon must not inflate the count forever. Make the threshold env-tunable following the existing `0`-disable sentinel convention. Confidence: 0.7
