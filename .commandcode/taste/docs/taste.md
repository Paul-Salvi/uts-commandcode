- When the API changes (new endpoints, updated routes, etc.), the Postman collection at `/smooth-pay/docs/postman/SmoothPay-API.postman_collection.json` must be updated to reflect the new endpoints, including request bodies, headers, auth, and test scripts. Treat this as part of the definition of done for any API change. Confidence: 0.85
- Before updating or renaming Postman endpoints, first verify that the backend controller/service code actually contains the corresponding endpoint — don't assume backend code exists based solely on prior planning or memory. Confidence: 0.80
- When updating a Postman collection, audit **all** endpoints against the actual source code — don't limit the update to only the changed ones. Verify request methods, field names, variable defaults, and response shapes match the implementation exactly, not keeping stale entries or production defaults. Confidence: 0.75
- Postman collections should be organized by **domain/functional area** (Auth, Agencies, Wallets, Payout Requests, etc.), not by project phases or releases. Phase-based grouping is stale by nature and doesn't reflect the API's actual structure. Confidence: 0.80
- Generated documentation output (HTML guides, reference docs, etc.) should be placed in a dedicated subfolder under `docs/` (e.g., `docs/product-docs/`) rather than directly in the root of `docs/` — this keeps the docs directory tidy and groups related generated artifacts together. Confidence: 0.85
- Every Postman collection request should include response validation test scripts (`pm.test(...)`) and collection variable chaining (setting IDs from responses for reuse in downstream requests) as standard best practice — not just the request definition alone. Confidence: 0.70
- Documentation/guide HTML sites should use a light theme (white background, dark text, warm gray borders) — not a dark theme. The Ledger design system light palette is the expected default: `#ffffff` body background, `#12151B` text, `#C8C6BE` borders, `#1a6d3b` emerald green accent. Confidence: 0.85
- End-user documentation (intended for Agents, Employees, or other non-developer audiences) must use plain English with no API calls, route paths, code formatting, or technical jargon. - Generated documentation output should be organized by target audience, not just by topic — place developer/technical docs (API references, architecture) separately from end-user/operations guides (workflow catalogs, role guides) in distinct subdirectories under `docs/`. Confidence: 0.75
- End-user documentation navigation should use user-friendly, role-oriented labels (e.g., "Daily Tasks", "Player Accounts", "Payment Pages") rather than technical system terms (e.g., "Workflows", "Platform Users", "Pay-In Pages").
