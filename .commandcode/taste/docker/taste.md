# docker
- Every service in the stack — backend APIs, frontend apps, and mock servers alike — should be containerized with a Dockerfile (multi-stage: deps → build → prod) and registered in docker-compose.yml so the full system can be `docker compose up --build`. Do not leave any service running as a bare process on the host. Confidence: 0.80
- After changing source code (especially backend API controllers or C# files), a plain `docker compose up -d --build` may still serve the old compiled binaries because Docker caches intermediate layers (e.g., `dotnet restore` and `dotnet publish` stages). To guarantee the latest code is picked up, force a full rebuild with `docker compose build --no-cache <service>` followed by `docker compose up -d <service>`. Don't assume the `--build` flag alone invalidates cached compiler output. Confidence: 0.80
- Docker Compose files belong in `./scripts/`, not scattered across project roots or mock directories. Confidence: 0.75
- When writing Docker Compose for a .NET service, grep the source code for all `IConfiguration` keys the app reads and include corresponding environment variables (using `__` for nested keys like `NexaPay__BaseUrl`), not just obvious ones like `ASPNETCORE_ENVIRONMENT`. Confidence: 0.70
- Configurable app settings (e.g., a new `Pagination` options section) must be wired into docker-compose.yml as environment variables using `__` nested-key syntax with `${VAR:-default}` host passthrough (e.g., `Pagination__DefaultPageSize=${PAGINATION_DEFAULT_PAGE_SIZE:-50}`), so deployments can tune values without code edits. The user explicitly asked for env-var wiring in docker-compose whenever settings are configurable ("is the values read from env variables? if yes make the change in docker-compose.yml"). Confidence: 0.85
- When the user asks to check whether a docker-compose.yml is "configured correctly", audit it against the actual sources of truth rather than reviewing the YAML in isolation: published port mappings vs the ports the containers actually listen on (Dockerfile `EXPOSE`, `ASPNETCORE_HTTP_PORTS`, the start command's port), build context vs the Dockerfile's `COPY` paths and sibling project references, env var names vs the config keys the app actually reads (`Program.cs`, `appsettings.json` — e.g. `ConnectionStrings__DefaultConnection`, not an invented name like `POSTGRES_CONNECTION` nothing reads), and stale service names/args copied from other projects. Report findings as a numbered list grouped by severity (build/runtime-breaking, unreachable, stale-but-harmless) and offer to apply the fixes. Confidence: 0.65
- When adding env vars for one payment provider (e.g., NexaPay) in Docker Compose, proactively check all sibling provider services (e.g., DollarPay) for their corresponding config keys and add them to the **main API container** that consumes them — don't wait for the user to ask about each one individually or misinterpret "check for X too" as checking the provider's own code. If a provider adapter is still a stub with no config keys, report that explicitly. Confidence: 0.75
- When changing a Dockerfile's build context to a different directory (e.g., from the repo root to `src/`), check for a `.dockerignore` at the NEW context root and add/copy one if missing — otherwise build artifacts like `bin`/`obj`/`node_modules` get sent to the daemon. Confidence: 0.65
- After editing docker-compose.yml or Dockerfiles, verify end-to-end before reporting done: rebuild the images (`docker compose build`) AND render the resolved config (`docker compose config`) to confirm variable interpolation, resolved paths, and port mappings are what you intended. Confidence: 0.65
- `http2: server: error reading preface` appearing in `docker compose up --build` output on this Docker Desktop host is a benign engine message during image export, not a build failure — confirm success via container state (built/recreated/running) rather than reporting it as an error. Confidence: 0.5
