- When passing arrays of objects to Next.js server actions, serialize to JSON string (`JSON.stringify`) and parse server-side to avoid `[Object]` serialization corruption. Confidence: 0.70
- Fetch initial data (dropdowns, selectors, form dependencies) server-side in the page component and pass as props to the client component — do not fetch them client-side via `useQuery` on mount, because they won't be ready when the component first renders. Confidence: 0.80
- Prefer server actions over client-side `fetch()` through Next.js rewrites when calling internal backend APIs — server actions call the backend directly via `process.env.API_BASE_URL` and are more reliable because they don't depend on rewrite configuration or Docker networking between the Next.js runtime and the backend. Confidence: 0.75
- When `next.config.ts` reads an environment variable at build time (e.g., `API_BASE_URL` for rewrite targets), setting it as a container runtime `environment:` in docker-compose is insufficient — the variable must be passed as a Docker build arg. Add `ARG VAR_NAME` + `ENV VAR_NAME=$VAR_NAME` in the Dockerfile build stage AND `build.args` in docker-compose.yml. Otherwise the Next.js build silently bakes in the default (usually `localhost`), breaking inter-container networking. Confidence: 0.85
- The project's pinned Next.js version has breaking changes vs. the model's training data — APIs, conventions, and file structure may all differ. Before writing any Next.js code, read the relevant guide bundled in `node_modules/next/dist/docs/` and heed deprecation notices; do not rely on training-data knowledge of Next.js. Confidence: 0.80
- When server actions handle file uploads, raise `serverActions.bodySizeLimit` (e.g., `'4mb'`) in `next.config.ts` under `experimental.serverActions` — the default 1MB request cap rejects larger uploads. Confidence: 0.7
- When the Next.js frontend consumes an ASP.NET Core/.NET API that returns PascalCase JSON (e.g., `Positions`, `WeightTotal`, `IsWeightValid`), explicitly map the raw response into the camelCase frontend types in the server action/fetch wrapper — do not pass the API's PascalCase objects straight into camelCase-typed components. A casing mismatch silently produces `undefined` fields and runtime 500s (e.g., `Cannot read properties of undefined (reading 'length')` in a `.reduce` over a missing array) or all-zero import results. This bug recurred in a new endpoint this session (import results showed 0s) and was fixed by mapping PascalCase raw types. Confidence: 0.9
- When a page needs a server-fetched list, an upload form, and a table that all share mutable state (e.g., an upload must refresh the tracker table immediately), consolidate them into a single page-level client component that owns the list state and passes a refresh callback to the upload form — do not split into separate server-rendered stat bars + a standalone client table + a no-op `onQueued` callback, which leaves the table stale after an upload until a manual refresh. Confidence: 0.7
- Do not call `revalidatePath` inside a server action when the client updates state from the action's return value — revalidation re-renders the current route and streams a fresh RSC payload in the same response, which can race with and clobber client-side `setState` that runs right after the action resolves (e.g., an upload-confirmation message never appears). If the target route is dynamic and fetches with `cache: "no-store"` on every visit, the revalidation is unnecessary — remove it and let the action return cleanly. Confidence: 0.8
- Organize frontend feature code under its own domain folder (e.g., `src/app/models/components/`) rather than nested inside another feature's folder (e.g., `src/app/import/components/`), even when one page consumes the other's components — a component belongs in the folder of the domain it represents, and cross-feature pages import it by path. Confidence: 0.7
- To confirm a client-rendered UI feature (modal, component, string) is actually deployed, grep the built JS chunks inside the running container (e.g., `docker exec <ui-container> sh -c "grep -rl '<marker string>' .next/static/chunks/"`) — client-component strings do not appear in the SSR HTML/RSC payload, so inspecting the deployed bundle is the proof that the code shipped. Note: code that runs server-side (server actions, fetch wrappers) is compiled into `.next/server/` chunks, not `.next/static/chunks/` — grep both locations depending on where the code executes. - For browser-initiated downloads of auth-gated files, route the request through a same-origin Next.js route handler (`app/api/.../route.ts`) rather than linking the backend URL directly — the handler reads the httpOnly auth cookie, attaches the Bearer token, fetches the file from the backend, and streams it back with a `content-disposition` header. The browser can't authenticate against the backend API directly (it only holds the cookie), so this proxy is the reliable download path. Confidence: 0.78
