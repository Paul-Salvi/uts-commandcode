# verification
- When verifying behavior that can be contaminated by concurrent writers or a stale running instance (e.g., two servers appending to one log), run the exact code under test in isolation against a scratch/throwaway fixture (temp dir) and assert invariant properties (size under cap, id monotonicity, no renumbering) — do not conclude correctness from a live environment with competing writers. Also check for pre-existing multi-writer hazards (e.g., two server processes sharing one data file with independent id counters) before attributing anomalies to new code. Confidence: 0.88
- When fixing or verifying subprocess/CLI handling (encoding, decode errors, arg passing), run the real code against a mock child executable — a small shim script that emits representative output including non-ASCII UTF-8 — and assert the parsed values; syntax checks alone don't prove the runtime path. On Windows, `.bat` shims mangle double-quoted JSON (cmd treats `"` specially), so use a `.py` entry script as the fake child instead. Confidence: 0.8
- When changing field names in one layer (mock server, adapter, types), proactively audit all consuming and adjacent layers (adapter code, admin pages, Postman collections, route handlers) for the same field names — a rename in one place creates a bug in every other place that references the old name. Confidence: 0.85
- After modifying API routes, verify by actually sending HTTP requests to the running service and inspecting response shapes field-by-field — building alone is not sufficient proof of correctness for API changes. Confidence: 0.85
- When verifying an error-handling or degradation path (file generation, mutation, import, etc.), always construct a deliberately-broken scenario (missing config, missing data, bad input) in addition to the happy path and assert the system lands in a clean FAILED/ERROR state with a readable message — never an unhandled exception or 500. Build success alone doesn't prove error paths degrade gracefully. Confidence: 0.83
- Do not claim a bug fix works based on build success alone — especially for UI bugs (e.g., "list not updating after create"). Build compilation only proves syntax/type correctness, not that the runtime flow actually works. Verify by testing the full user interaction flow end-to-end in the running app (perform the mutation, check the UI updates, inspect network requests) before declaring the fix done. Claiming success without runtime verification will be called out as hallucination. Confidence: 0.85
- Ground all analysis and reports in actual code verification, not planning documents (UI_IMPLEMENTATION_PLAN.md, AGENTS.md, copilot-instructions.md, etc.). If a planning doc contradicts the code, cite both explicitly. Confidence: 0.85
- When verifying whether a service or adapter is fully integrated, audit across ALL layers — project references, interface contracts, implementation classes, DI registration, config binding, and domain entity support — and benchmark against a known-working sibling (e.g., compare DollarPay against NexaPay). Don't accept stub projects or file existence as proof of integration. Confidence: 0.75
- After writing code, run the actual build command (dotnet build, npm run build, etc.) to verify it compiles — don't rely solely on file inspection or assume correctness. If the build tool isn't available, report that explicitly rather than claiming success. Confidence: 0.80
- After applying DB schema changes and before deploying, verify migrations were actually applied by checking the database directly (psql query for new columns or `__EFMigrationsHistory` entries) — do not rely on the migration tool's exit code or the app's `MigrateAsync()` startup call alone. Confidence: 0.85
- Treat a warning-free build as part of the done definition: proactively fix compiler warnings (e.g., nullable-reference hints in test fakes) instead of leaving them, and report "build clean (0 warnings)" when confirming completion — a passing build with warnings is not fully clean. Confidence: 0.65
- When extending a production class with new constructor dependencies, update the affected test fakes and constructor calls in the same pass, then run the full existing test suite to confirm a green baseline BEFORE writing the new tests — a passing baseline makes failures in the new tests attributable to the new code rather than the refactor. Confidence: 0.7
- For a change spanning backend + frontend, the done-definition verification ladder is: backend `dotnet build` clean + full `dotnet test` suite green, then frontend `npx tsc --noEmit`, `npx eslint src`, and `npm run build` all clean — before reporting completion. Confidence: 0.65
- When a bug fix involves threading/asyncio setup that cannot be reproduced end-to-end without a real external dependency (e.g., a Telegram bot token to start `run_polling()`), verify by writing a standalone focused test that replicates the exact thread/event-loop structure with fakes (fake app/bot objects, monkeypatched worker) and asserts the conflict is resolved (worker task runs, main thread can still run its own loop) — syntax checks alone don't prove the runtime threading path. Confidence: 0.8
- When a bug is a process-level crash (e.g., an unhandled `'error'` event on a spawned child), verify the fix by reproducing the exact failure in a standalone harness: extract the function under test and run it with a mocked dependency that emits the identical error asynchronously (matching the user's stack trace, e.g., `spawn cmd.exe ENOENT`), then assert the process stays alive — the happy path or a syntax check cannot prove a crash fix. Confidence: 0.8
- When testing CLI-wrapper fallback/recovery logic with a fake, the fake must emit the failure through the SAME channel the real CLI uses (parsed error field vs stdout vs stderr) — a mock that places the error in the wrong channel produces a false pass and hides detection bugs (a stale-resume fallback test failed until detection was widened to include the parsed error field). Also assert both recovery branches: retry-succeeds (new session recorded) AND retry-also-fails (stale state still cleared). Confidence: 0.7
- When a CLI fix passes mock-based tests but still fails against the real tool, the mock's value SHAPES must mirror the real output exactly — e.g., command-code emits `finalText: ""` (empty string) on error results, so a detection check like `final_text is None` never fires in production even though it passes against a mock returning `None`. Prefer truthiness-based checks (`not final_text`) for optional CLI result fields, and shape test fakes from real error output captured in logs, not from assumptions. Confidence: 0.75
